# Data Model: Real-Time Chat & Messaging Service

**Feature**: `specs/001-realtime-chat-service/spec.md` · **Plan**: [plan.md](./plan.md)
**Store**: PostgreSQL `chatDb` (EF Core 9 + Npgsql) · **IDs**: Conversation/Message `long` Snowflake (IdGen node 5); users are Keycloak `sub` strings

All timestamps are UTC (`timestamptz`). All `long` ids are Snowflake values.
User identity is the Keycloak `sub` claim (`varchar(255)`), the same identity the
rest of the repository uses (`Post.AuthorId`, `Connection.RequesterId`, gateway
`X-User-Id`). User Service numeric ids are never required, so no cross-service
lookup is needed (2026-11-01 decision).
EF Core configurations follow EngagementService precedent
(`IEntityTypeConfiguration<T>`, `ValueGeneratedNever()`, explicit table/index names).

## Conversation

| Field | Type | Rules |
|---|---|---|
| `Id` | `long` PK | Snowflake, `ValueGeneratedNever()` |
| `Participant1Id` | `varchar(255)` | MUST be the ordinal `min(subA, subB)` Keycloak subject |
| `Participant2Id` | `varchar(255)` | MUST be the ordinal `max(subA, subB)` Keycloak subject; MUST differ from Participant1Id |
| `CreatedAt` | `timestamptz` | set once on creation |
| `LastMessageAt` | `timestamptz` | updated in the same transaction as each new message; monotonic |

Constraints/indexes:
- **Unique index** `(Participant1Id, Participant2Id)` — FR-003/SC-006; the pair is
  normalized so `(A,B)` and `(B,A)` collide by design.
- Index `(LastMessageAt DESC)` for conversation lists (FR-013).
- Insert race: catch unique violation → re-read existing row (research R11).

## Message

| Field | Type | Rules |
|---|---|---|
| `Id` | `long` PK | Snowflake; conversation ordering key (FR-006) |
| `ConversationId` | `long` | FK → Conversation; indexed with `Id` |
| `SenderId` | `varchar(255)` | Keycloak subject; MUST be a participant of the conversation |
| `ClientMessageId` | `Guid` | client-generated; makes send/retry idempotent (FR-019/FR-023) |
| `Ciphertext` | `bytea` | E2E payload; server MUST NOT inspect (FR-021); max 16 KiB |
| `Nonce` | `bytea(12)` | AES-GCM nonce generated by sender |
| `Algorithm` | `varchar(32)` | `AES-256-GCM-v1` |
| `SentAt` | `timestamptz` | server receipt time |
| `ReadAtUtc` | `timestamptz NULL` | set once via bulk "mark read up to" (FR-010/FR-011) |

Constraints/indexes:
- **Unique** `(ConversationId, SenderId, ClientMessageId)` — de-duplicates send
  retries and double taps (FR-019/FR-023).
- Index `(ConversationId, Id DESC)` — keyset history paging (FR-022, research R9).
- Partial index `(ConversationId) WHERE "ReadAtUtc" IS NULL` — unread counts.
- Plaintext length (2,000 chars) is enforced client-side (server cannot see
  plaintext); the server enforces the ciphertext byte ceiling and rejects
  oversize payloads with clear feedback (FR-018).

## ConversationKeyEnvelope

| Field | Type | Rules |
|---|---|---|
| `ConversationId` | `long` | part of composite PK |
| `DeviceId` | `Guid` | part of composite PK; recipient device |
| `WrappedKey` | `bytea` | conversation key K_c encrypted to the device's P-256 public key |
| `Nonce` | `bytea(12)` | wrapping nonce |
| `CreatedAt` | `timestamptz` | |

- Composite PK `(ConversationId, DeviceId)`. Uploaded by a participant after
  conversation creation (initiator wraps K_c for every active device of both
  users). A device can unwrap only envelopes addressed to it (research R3).
- New device after message history exists: cannot decrypt prior messages unless
  a peer re-wraps K_c — documented v1 limitation.

## Lifecycle & state transitions

```text
Conversation: absent --first message--> created (LastMessageAt = now)
              existing --new message--> LastMessageAt advanced (same tx)

Message:      client draft --SendMessage/retry--> persisted (ReadAtUtc NULL)
              persisted --recipient views--> ReadAtUtc set once (bulk up-to)
              send failure (not persisted) --> client-side "failed" state,
                                              retry reuses ClientMessageId

Notification: message persisted + recipient offline --> Outbox pending
              Debezium --> Kafka --> consumer --> email/push attempt
              success/final-failure --> Inbox recorded, offset committed
```

Ordering invariant: `Message.Id` strictly increases per conversation and is the
single ordering key for history and paging. `ReadAtUtc` transitions only
NULL → value (idempotent updates ignore non-NULL rows).

## Redis key schema (ephemeral — never source of truth)

| Key pattern | Type | TTL | Purpose |
|---|---|---|---|
| `chat:presence:{userId}` | SET of connection ids | 90 s, refreshed by heartbeat | online while non-empty (SC-003) |
| `chat:typing:{conversationId}:{userId}` | string | 5 s | typing indicator auto-expiry (SC-002) |
| SignalR backplane channels | provider-managed | — | cross-replica broadcast (FR-007) |

Presence/typing state is derived from live sessions and is never persisted to
PostgreSQL (FR-008/FR-009).

## Validation rules → requirements

| Rule | Requirement |
|---|---|
| Send only between active connections | FR-001/FR-002 |
| Exactly one conversation per normalized pair | FR-003/SC-006, unique index |
| Ciphertext well-formed, nonce length 12, algorithm allowed | FR-021 |
| Sender is a participant; recipient device envelopes only to participant devices | FR-017 |
| `ClientMessageId` unique per sender/conversation | FR-019/FR-023 |
| `upToMessageId` belongs to the conversation | FR-011 |
| Message ordering = `Id` order | FR-006 |
| No plaintext content columns exist | FR-021 |

## Volume assumptions

- 10,000 messages per conversation (SC-007) with paged reads.
- 1,000 concurrent sessions per instance (SC-008); conversations scale linearly
  with message count via the `(ConversationId, Id DESC)` index.
- Projections are small (one row per connection pair / user) and rebuildable
  from Kafka history.
